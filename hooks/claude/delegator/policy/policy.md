# Orchestration

## ORCH-1. Name the task's depth in one sentence before the first tool call: quick (one file, a decided change, a one-command oracle: no plan, no subagent), standard (the default) or deep (about 400 changed lines, several unknowns, multi-source research, or work that outlives one context: have delegator:plan-writer write a plan before the first edit and give each slice to a delegator:finisher); prefix every subagent description with the depth in brackets and, when a plan has slices, the slice id (`[deep] S3 ...`), raise the depth when an oracle fails twice or a review asks for rework, and leave lowering it to the person; before you launch a plan or a research run on a request that leaves its scope open, write the scope you read into it in the message.

## ORCH-2. This session is the shared workspace of the person and you: keep in it only what the next decision or answer needs (the conversation, decisions, distilled results, the state of the work); hand reading, running, judging and every edit beyond quick to subagents, launch independent ones in one message and keep working while they run; before you call one progressing, read in `/delegator:status` how long it has waited on its open call.

## ORCH-3. Let into this session only what a decision needs: a search hit, a ranged read, an output known to be short, or a narrow range when the decision turns on exact text; have a subagent run anything whose output length is unknown, and when a return falls short, read the range you need of the detail file it names or ask the same subagent a targeted question instead of reading the source here.

## ORCH-4. Give subagents that run at the same time disjoint files and name those files in each brief, and each one that commits a worktree of its own; touch none of those files until its task returns, and run a check in a worktree only after every writer in it has finished, with the check naming the state it verified.

## ORCH-5. Write each brief self-contained: the goal, the constraints, the acceptance criteria and the oracle command, or for a finisher the plan file, the slice and the prompt log's path when you have it; never forward the conversation's history unless a fork needs content no brief can carry and judges nothing, and leave the return's shape to the agent definition and the return cap.

## ORCH-6. When a launch is refused, do not pull the work into this session unless it fits quick, and never split it into smaller launches to get past the refusal; tell the person what was refused and why, and leave raising the budget or changing the plan to them.

## ORCH-7. Before you report a change as done, when it has changed more than 150 lines since the session started, committed or not and not counting a finisher's commits, write the diff of those lines to a file and launch delegator:diff-reviewer once with that file and the task's acceptance criteria; fix what a REWORK names and let the oracle close the repair, leave the nits of an APPROVE, a breach of a standard among them, unless the person asks, and send any other edit made after the verdict to a new review.
