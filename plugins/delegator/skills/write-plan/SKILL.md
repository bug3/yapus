---
name: write-plan
description: Have the plan of deep work written before its first edit, reviewed, decided with the person and built slice by slice. Use when ORCH-1 rates a task deep or the person asks for a plan.
---

- Launch `delegator:plan-writer` with the topic, the sources and the questions the plan must settle; it writes the plan to `.yapus/plans/<YYYY-MM>/<topic>/plan.md` in the project's root, and you name that path in every brief that rests on it.
- On the plan-writer's first return, launch in one message, first and before the first edit, `delegator:plan-reviewer` once on the plan file and its acceptance criteria when the plan touches more than one module or a public interface, then the subagents that measure the facts it returns as unmeasured and run the probes and readings the plan names, the short ones together in one subagent, each working outside the repository.
- When the plan-writer first returns the plan, read it against what the person said in the session while the plan-reviewer runs, and add each point it misses or contradicts to the defects you send the plan-writer, asking the person each one that is theirs to decide.
- After the review, or at once when the plan needs none, ask the person the open decisions in one batch, in calls of up to four questions back to back with the most consequential first, then send the plan-writer the defects, the measurements and the answers in one message to fold each into the section it names.
- Brief the plan-writer and fold each review defect by the plan-writer's own rules: one intent per commit, not per slice, and no need for the slice of approved text, README and versions on a slice whose code its criteria do not run, since its last id already lands it last.
- Give each finisher one slice of the plan, with the brief ORCH-5 names for it; launch at once every slice whose needed slices have landed and whose files are disjoint from each other's and from those of the running slices, each in a worktree and branch of its own from the tested tip of the landing branch, both named in the brief.
- Land the finishers' commits on one branch in the plan's order, by a cherry-pick loop that stops at the first conflict, when a later slice needs them and at the end, the version commit after the whole review below when it applies, not before every launch, and have a subagent run the oracle on the landed tip; while the next slices run, have one run it on each landed commit in a separate worktree.
- When you send a finisher back after its return, ask for new commits on top of its own or for a new branch from a named commit, never for a reset or an amend, name each file the request adds to its slice, and land its slice only after its last return.
- When every slice of the plan has returned, and the plan holds five or more slices or slices that share state or a code path, land every commit but the version commit, then in one message launch `delegator:diff-reviewer` on the whole diff of the landing branch and start each other review of the whole change that the person or the project's instructions name, and wait for all of them; land the version commit after the commits that repair their findings, and run on the repaired tip each measurement the plan names for the whole.
- Ask the person, with the question tool, only the open decisions on architecture, authentication, data migration, the shape of a public interface, a dependency or technology choice, or one the project's instructions leave to the person: one question per decision, your recommendation first, its context inside the question; ask each name the person will type or see that the work adds as a question of its own with alternatives, before the first finisher starts and never only inside a text put up for approval.
- Ask each decision a slice's return leaves for the person in the turn that return arrives, while the other slices run, and make the answer a new slice that needs each slice that changes one of its files; hold no other slice for it, the slice of approved text included.
- Take every other open decision as the plan recommends, and record it in Decisions as taken by you and open to the person's override.
- Record each decision the person makes in Decisions as they make it, and update Status each time a slice returns.
